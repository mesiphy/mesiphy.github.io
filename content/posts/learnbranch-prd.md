这份 PRD 不是写给“未来某一天”的愿望清单，而是用当前代码、验收记录和未完成项重新校准的一版产品基线。它描述的是 LearnBranch 0.1 开发版：Windows 原生闭环和当前用户安装技术链已经跑通，但生产签名、自动更新、跨平台分发与用户 Alpha 尚未完成，因此不能把“技术可运行”写成“已经公开发布”。

版本：PRD 1.0；状态：开发版基线；更新日期：2026 年 8 月 19 日。

## 一、产品概述

### 1.1 产品定义

LearnBranch 是一款用 AI 分支问答构建学习知识树的桌面应用。用户从一个根问题开始，在任意历史节点继续追问；每个分支只继承自己的祖先上下文。AI 回答先进入待审核草稿，用户确认后才写入本地 Markdown，并可进一步生成整支笔记、学习总结与 Obsidian JSON Canvas 快照。

### 1.2 用户问题

线性 AI 对话在短任务中高效，但进入学习和研究场景后会出现四个问题：

1. 一个回答里有多个值得深入的概念，继续追问会把主线和旁支混在一起。
2. 返回旧话题时，用户很难记得当时的上下文，更难比较兄弟路径。
3. AI 回答自动进入历史记录，却没有“我已审核并愿意长期保存”的明确动作。
4. 资料被锁在产品内部；迁移、外部编辑、备份和故障恢复缺少可控边界。

### 1.3 核心 Job to be Done

> 当我围绕一个复杂主题学习时，我希望从任意结论继续开辟一条独立路径，同时保留它继承的上下文和来源；当探索结束后，我希望把确认过的内容整理成普通 Markdown，以便在 Obsidian 或文件系统里长期使用。

## 二、目标用户与场景

### 2.1 核心用户

- 已经使用 AI 辅助学习、会对同一主题连续追问的人。
- 重视本地文件、Markdown、Obsidian 或 Git 工作流的人。
- 愿意主动整理学习路径，而不是只消费一次性答案的人。
- 当前 Alpha 优先面向 Windows 桌面用户；不以移动端轻问答作为首发场景。

### 2.2 非目标用户

- 只需要问一次就离开的轻量聊天用户。
- 需要多人实时协作、权限管理和企业知识库的人。
- 以自由脑暴和精细排版为主、期待完整脑图编辑器的人。
- 需要自动摄取大量网页、音视频和企业数据源的人。

### 2.3 核心场景

**场景 A：概念学习。** 用户从“Transformer 为什么需要注意力机制”开始，把前置知识、澄清、应用和质疑分别建成分支，随时回到任意节点继续。

**场景 B：长文研究。** 用户把确认过的节点保存在 Vault，完成一轮探索后生成带来源节点的学习顺序、核心洞察和未解决问题。

**场景 C：跨应用复用。** 用户在 Obsidian 中阅读或编辑 Markdown，并把当前会话导出为标准 JSON Canvas；即使卸载 LearnBranch，文件仍可打开。

## 三、目标、非目标与原则

### 3.1 版本目标

1. 跑通“根问题—分支追问—草稿审核—确认入库—整理/导出”的完整闭环。
2. 让用户始终能看见当前节点在树中的位置和祖先路径。
3. 让生成失败、外部编辑冲突、删除和旧数据导入都有明确恢复路径。
4. 证明本地 Markdown 不只是存储实现，而会被用户在应用外重新使用。

### 3.2 本版本不做

- 任意连线、多父节点和自动分支合并。
- 实时多人协作。
- 自动把整篇来源笔记发送给模型。
- Canvas 与内部树的双向实时同步。
- 跨会话 RAG、间隔复习和自动掌握度判断。
- 在生产签名和用户 Alpha 完成前提供公开下载安装承诺。

### 3.3 产品原则

- **路径优先：** 分支只继承祖先，不把兄弟分支混入上下文。
- **人工确认：** 生成成功不等于成为用户笔记。
- **本地可读：** Markdown 是权威数据，专有运行时状态不能成为唯一副本。
- **可恢复：** 失败节点留在原位，删除进入回收目录，冲突时停止覆盖。
- **派生可再生：** 总结、整支笔记和 Canvas 都是输出，不反向篡改源节点。

## 四、信息架构与对象模型

桌面界面采用三块区域：左侧会话列表、中部节点详情主工作区、右侧紧凑关系图。用户阅读长回答时，中部优先；需要换路径时使用右图；专注模式可临时收起两侧。

核心对象只有四类：

| 对象 | 关键字段 | 产品含义 |
| --- | --- | --- |
| Session | 标题、根节点、状态、最新总结/Canvas 路径 | 一次围绕同一主题的学习过程 |
| Node | 父节点、问题、回答、问题类型、学习/生成状态、请求 ID | 一次有位置的学习追问 |
| Answer Draft | 节点、请求 ID、草稿正文、生成时间 | 尚未进入用户 Markdown 的 AI 初版 |
| Derived Output | 总结、整支笔记、Canvas | 可以重新生成、不可替代源节点的交付物 |

问题同时保留两个文本字段：`question` 是图谱和页面使用的短标题，最长 60 个字符；`questionDescription` 是实际发送给模型的完整问题。这样既避免图中塞满长句，也不迫使用户为了界面整洁牺牲提示信息。

节点有两套相互独立的状态：

- 生成状态：`draft / generating / ready / failed`，描述系统过程。
- 学习状态：`todo / exploring / understood / uncertain`，只表达用户判断。

产品不能因为模型成功回答，就自动把学习状态改成“已理解”。

## 五、功能需求

### P0-1 首次配置

用户可选择并持久化一个 Tauri 专用 Vault，配置或清除 DeepSeek API Key，并测试连接。普通设置存入 Tauri Store；Key 存入操作系统凭据库，读取配置时只返回“是否已配置”，不回传明文。

**验收：** 未选 Vault 或未配置 Key 时给出下一步；切换 Vault 后刷新会话；日志、IPC 响应与普通配置不得出现 Key。

### P0-2 创建会话和根问题

用户输入会话标题、根问题、模型与是否深度思考。系统先创建 Session 与根节点，再请求 AI；即使网络失败，问题仍保存在磁盘并可重试。

**验收：** 会话和节点 ID 唯一；根节点 `parentId = null`；失败后原节点进入 `failed`，不新增一个含义重复的节点。

### P0-3 从任意节点创建分支

用户在当前选中节点点击“创建分支”，填写短标题、完整问题描述、问题类型、模型与思考模式。系统只构建根到父节点的祖先链上下文，不读取兄弟分支。

**验收：** 新节点挂在明确父节点下；提交期间防止重复点击；单会话最多 50 个节点；同一会话生成与整理串行化。

### P0-4 审核并保存 AI 草稿

生成结果先写入应用数据目录的 Answer Draft，不直接成为节点 Markdown 正文。详情页显示“AI 草稿待审核”，用户可在 Markdown/实时预览双栏中修改回答，并可填写更易读的笔记文件名；确认后才写入 Vault 并删除草稿。

**验收：** 未确认草稿不会被展示为“已同步 Obsidian”；保存前检查节点快照和文件版本；外部修改发生后停止覆盖并要求重新加载。

### P0-5 浏览与定位

左侧会话列表支持搜索、选择和节点计数。中部展示问题、完整描述、回答、祖先面包屑及元数据。右图支持节点选择、缩放、平移、适配视图和重新布局；选择节点后同步更新中部详情并突出祖先路径。

**验收：** 选择只是导航，不修改父子关系或学习状态；右图可折叠为 48px 导航栏；960×640 最小窗口不产生整页横向溢出。

### P0-6 编辑、分类与删除

用户可修改已确认回答、笔记文件名、问题类型和学习状态。非根节点允许连同全部后代删除，文件移动到 `.learnbranch-trash`；根节点在界面和 Rust 后端双重禁止删除。

**验收：** 删除前显示后代数量；部分移动失败时尝试回滚；删除后选择回到父节点；应用重启后可以通过复制回原路径并重新扫描恢复。

### P0-7 整理与导出

用户可以执行三种派生操作：

1. 整理整场会话，生成学习顺序、核心洞察、未解决问题和来源节点。
2. 把当前节点与全部后代合并为一份整支 Markdown 笔记。
3. 导出标准 JSON Canvas 1.0 快照，节点指向实际 Vault 文件，边表达父子关系。

**验收：** 输出使用版本化文件名，不覆盖旧结果；整理引用的节点必须真实存在；无效结果不写成正式总结；导出不得修改源树。

### P0-8 旧数据单向导入

旧 Obsidian 插件与 Tauri 的目录结构不同，不能直接共用。设置页允许选择旧目录，先只读扫描并预览，再在写入前创建逐文件备份。未知 Schema、重复 ID、损坏树、超过节点上限、目标冲突或源指纹变化均阻断导入。

**验收：** 重复导入保持幂等；中途失败回滚本批次目标文件但保留备份；绝不改写源目录；界面明确说明这不是双向同步。

## 六、关键业务规则

| 编号 | 规则 |
| --- | --- |
| BR-01 | 一棵会话树只有一个根节点，节点只有一个父节点 |
| BR-02 | 分支上下文 = 当前父节点的祖先链；兄弟与后代不得进入 |
| BR-03 | 单会话最多 50 个节点 |
| BR-04 | `requestId` 决定响应是否仍是最新；迟到响应不得覆盖新请求 |
| BR-05 | AI 草稿与已确认 Markdown 是两份不同状态，不得混淆 |
| BR-06 | `understood` 只能由用户设置，系统不代替用户判断掌握程度 |
| BR-07 | 根节点不可通过分支删除能力删除 |
| BR-08 | Canvas、总结、整支笔记均为派生输出 |
| BR-09 | 旧插件和 Tauri 必须使用隔离目录，只允许受支持的单向导入 |
| BR-10 | 任意危险写入前必须校验路径、版本、请求或源指纹中的适用项 |

## 七、非功能需求

### 可靠性

- 同会话操作串行化；不同会话允许并行。
- 写入使用文件锁、版本检查和节点快照校验。
- 请求失败保留节点、问题、错误与尝试次数。
- 应用强制终止后，已确认 Vault 文件和待审核草稿不得损坏。

### 安全与隐私

- 应用直接从桌面后端请求 DeepSeek，没有中转服务和遥测后端。
- API Key 进入操作系统凭据库。
- 默认只发送当前问题与允许的祖先上下文。
- 草稿、失败整理和 Vault 正文可能包含私人内容，不得进入普通日志或公开测试证据。

### 可访问性与界面

- 状态不能只靠颜色表达，必须同时有文字或图标。
- 水彩纸与深色主题使用同一套语义色，切换主题不重建图布局。
- 长 Markdown、代码块和表格以中部阅读体验为优先。
- 危险操作必须明确对象、范围和恢复方式。

## 八、指标与验证计划

当前产品没有遥测后端，所以 Alpha 阶段采用脱敏事件表与访谈记录，不为了“有数据”提前上传用户内容。

### 北极星指标

创建至少 3 个分支的会话中，完成一次整理，并在 7 天内重新打开节点或整理结果的会话比例。

### 漏斗指标

| 阶段 | 指标 | 用来判断什么 |
| --- | --- | --- |
| 开始 | 首次配置后成功创建根问题的比例 | 安装与配置是否阻断 |
| 探索 | 每个有效会话的分支数、最大深度 | 用户是否真的需要非线性结构 |
| 审核 | AI 草稿打开率、修改率、确认率 | 人工审核是否产生价值 |
| 整理 | 3+ 分支会话的整理率 | 结构是否能收敛为结果 |
| 复用 | 在 Obsidian/文件系统打开输出、7 日重开率 | 本地开放格式是否形成留存 |
| 可靠性 | 失败重试成功率、冲突后数据丢失数 | 恢复设计是否可信 |

Alpha 的硬底线是用户内容零丢失。增长指标再漂亮，只要出现不可恢复覆盖，就不能进入更大范围发布。

## 九、发布门槛

当前已经完成 Windows 原生真实 API 闭环、数据与 Obsidian 交付验收，以及 NSIS 的安装、升级、降级阻断、卸载、重装和强制终止恢复测试。但公开发布仍需：

1. Windows 受信任生产证书签名与时间戳。
2. 自动更新、失败回滚和发布通道验证。
3. macOS 签名/公证与 Linux 原生分发验收，或明确首发只支持 Windows。
4. 5～8 人、两周 Tauri 内部 Alpha，完成核心任务与数据安全复盘。

只有同时跨过“产品闭环、数据安全、安装可信、真实用户”四道门槛，0.1 才能从开发版变成可公开承诺的产品。
