Agent coding 在项目早期是加速器,在后期维护阶段是双刃剑，**对于编程基础一般的开发者，宁慢勿急，否则就是灾难，对自己的成长是，对项目的推进也是。**。

## 项目早期:验证速度碾压一切

### 优势是真实的

**快速试错的价值被低估了。** 一个想法从脑子里到能点击的原型,传统方式可能需要一周——搭环境、选框架、写模板。Agent coding 能把这个周期压到一天之内。

这种速度优势在三个场景下尤其明显:

| 场景 | 传统方式 | Agent coding | 差距来源 |
| --- | --- | --- | --- |
| 技术选型验证 | 看文档→写 demo→对比 | 直接让 AI 实现三个方案 | 省去学习曲线 |
| API 集成测试 | 读接口文档→写调用代码 | 给 API 文档让 AI 生成 | 减少理解成本 |
| UI 原型搭建 | 从零写 HTML/CSS | 描述需求直接生成 | 跳过重复劳动 |

我上个月用 Claude 搭了一个内部工具的原型(参考LearnBranch那个项目的开发记录文档),从需求到可演示的版本用了不到 4 小时。如果自己写,光是配置 Vite + TypeScript + TailwindCSS 的环境就要半天，这还没有考虑学习成本😭。

**降低技术栈的入门门槛。** 不熟悉的语言或框架,以前需要先啃文档,现在可以边做边学。想试试 Rust 写个 CLI?不需要先花一周学所有权系统,让 AI 写个能跑的版本,再从生成的代码里反推概念。

这不是鼓励「不学就用」,而是改变了学习路径:从抽象到具体变成从具体到抽象,对很多人来说后者效率更高。
**这也反过来我们反思什么是学习————通过概念的理解，最终构建起自己的心智模型，如果没有，学习就没有完成。遗憾的是，我们是被推着走的，很多时候，会被所谓的“没有精力、没有必要、能跑就行”之类的借口压下心里那份担忧，可鸵鸟终究要面对现实**
### 但埋下的隐患是真实的

**代码质量参差不齐,且不容易察觉。** AI 生成的代码「能跑」和「写得好」之间有巨大的灰度空间。

早期常见的坑:
- **错误处理缺失或敷衍** — 只有 happy path,边界情况全靠运气
- **依赖选择不合理** — 为了实现功能引入了重量级的库,其实标准库够用
- **架构缺乏扩展性** — 能实现当前需求,但加新功能就得大改
- **大量的门禁验证** - 点名批评GPT，尤其是5.6sol
- **代码可读性极差** - 越差越不想读，越不想读越差，最终整个项目成为屎山。
更危险的是,早期阶段你通常在快速迭代,**没时间 review 每一行生成的代码**。问题会被埋进代码库,等到项目做大了才暴露。

**对系统理解不够深入。** 用 AI 快速搭出来的项目,最大的风险是你对架构的理解是浅层的。

举个例子:你让 AI 帮你搭了一个带认证的后端服务,它用了 JWT + Redis。你知道流程跑通了,但不一定清楚:
- Token 的刷新策略为什么这么设计?
- Redis 挂了会发生什么?
- 并发情况下会不会有竞态条件?

这些问题在原型阶段不重要,但进入生产后会要命。

## 后期维护:成本会在意想不到的地方出现

### 主要挑战

**技术债的复利效应。** 早期用 AI 写的代码,如果没有及时 review 和重构,会随着项目增长变成负资产。

**理解成本高于从头写。** 读别人的代码本来就难,读 AI 的代码更难,因为它的实现方式可能不符合人类的思维习惯。

典型现象:
- 函数嵌套层级深,为了「完整性」塞进了很多暂时用不到的逻辑
- 变量命名过于通用,`data`、`result`、`temp` 满天飞
- 注释要么没有,要么是复读机式的废话注释

维护这样的代码,你会发现**改一个小功能需要先花半天理解周边逻辑**,效率反而比自己从头写更低。

**重构的心理门槛更高。** 自己写的代码,改起来心里有数。AI 生成的代码,你不确定某段逻辑是不是有隐含的依赖,不敢动。

结果就是技术债不断累积,最后只能整个模块推倒重来。

### 但也不是一无是处

后期维护阶段,Agent coding 在特定任务上仍然有价值:

**重复性的体力活。** 写测试、补文档、生成类型定义,这些事情机械但必要,AI 做起来又快又稳。

```typescript
// 你已经有实现,让 AI 帮你生成对应的测试
describe('UserService', () => {
  it('should create user with valid email', async () => {
    // AI 生成的测试用例覆盖了各种边界情况
  });
});
```

**遗留代码的理解辅助。** 接手别人的老项目,让 AI 先帮你梳理代码结构、解释关键函数的作用,比自己盲目啃快得多。

**非核心模块的实现。** 项目里总有一些「必须有但不是核心竞争力」的功能,比如导出 CSV、发邮件、生成缩略图。这些用 AI 快速实现,把精力留给核心逻辑。

## 实际建议

**用的越多，消耗的token越多(codex已经破百亿了，都是白花花的钱呐😭)，我越认为所谓的 “AI”离真正的人工智能还很远。**
**AI只是个工具，一个试图从人类产出的海量结果中发现人类智能pattern的一个工具。** 模型只是试图从数据中发现数据产生的“pattern”。任何模型都是，机器学习、深度学习是，目前的基于Transformer架构的LLMs也是。
我还记得一个典型的深度学习模型的案例————一个针对CT结果进行识别病例的模型，训练之后的正确率很高，但是研究人员验证之后发现：模型学到的只是按照不同的医院的结果打分，有的医院全打对，有的医院全打错，最终训练出来一个准确率很高，但其实根本没有发现真实“pattern”的模型。LLM 是否也是这样呢？LLM学到了一个“与人类智能表现类似的pattern”，但实际跟上面的深度学习模型一样，学到的不是我们人类所希望的“pattern”呢？

以上是“杞人忧天”，看官们当做“胡说八道”图一乐就行😊。至少现在还能用，希望未来能更好用。
下面是一些实践总结：

关键在于**意识到这个工具的边界**:
- 用它加速不重要的部分
- 但核心逻辑、架构决策、安全相关的代码,必须自己拿主意
- 早期生成的代码,要在项目稳定后系统地 review 和重构

AI 辅助编程的最佳实践,可能不是「用 AI 写所有代码」,而是「用 AI 处理样板代码和重复劳动,把时间花在真正需要思考的地方」。

毕竟,编程的核心从来不是敲代码的速度,而是理解问题、设计方案、做出权衡的能力。这部分,至少在可见的未来,还是得自己来。
**人类最重要的权利，是自主权。失去对coding的控制，coding出来的东西跟你有什么关系呢？**
