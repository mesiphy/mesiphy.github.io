LearnBranch 的起点不是“做一张漂亮的知识图谱”，而是一个很具体的不适：AI 对话稍微深入，就会出现多个都值得继续的问题。在线性窗口里追问一个，其他岔路会被挤走；复制成多段聊天，又很快忘记它们从哪里分开。

于是产品问题被改写成：能不能让每次追问都成为一个有父节点、有上下文、有状态、最终还能回到本地笔记的学习节点？

这篇文章记录当前仓库所能证明的构建过程。代码仍是开发版，仓库也保留了大量历史蓝图；我会把“曾经计划”“当前实现”和“已经验收”分开写。

## 第一阶段：先把对话变成树

最早的实现是一条 Obsidian 插件轨道。选择它有很现实的理由：目标用户本来就在 Obsidian 里写 Markdown，插件可以直接使用 Vault、命令与文件 API，验证“问答节点是否值得长期保留”比先解决桌面分发便宜得多。

这个阶段确定了几个后来没有改变的领域模型：

- 一个 Session 只有一个根节点。
- 每个 Node 只有一个父节点，结构是树而不是任意图。
- 分支问题只继承祖先链，兄弟分支不进入模型上下文。
- 问题类型与学习状态由用户明确标记。
- 会话整理必须把结论引用回真实节点。
- Markdown + frontmatter 是权威数据，Canvas 是派生输出。

限制单父节点看似保守，却让上下文可以被解释：沿父指针回到根，反转后就是模型输入路径。若一开始允许任意合并，产品必须立刻回答“两个分支冲突时以谁为准”“合并后重试继承什么”等更难的问题。

## 第二阶段：原型暴露了“图不能抢走阅读”

产品早期曾把地图当主界面：左边会话，中间大图，右边节点面板。它非常像一个“可视化 AI 产品”，但长回答、代码块和表格被压缩在狭窄区域，地图占据大量空间却主要承担定位。

最终界面改成：

```text
┌──────────────┬──────────────────────────────┬────────────────┐
│ 会话列表      │ 节点详情主工作区              │ 紧凑关系图      │
│ 搜索/节点数   │ 问题、回答、编辑、祖先路径     │ 选择/缩放/布局  │
└──────────────┴──────────────────────────────┴────────────────┘
```

这个改动背后是一条很朴素的产品判断：学习的主动作是阅读和修改，图谱是导航，不是舞台布景。右图可以折叠成 48px 导航栏，中部可以进入专注阅读；选中节点时突出其祖先路径，让“我在树的哪里”保持可见。

原型阶段还拆开了一个容易被忽略的字段：图谱上的短标题与发送给 AI 的完整问题不是同一段文本。现在 `question` 负责页面标题和节点标签，`questionDescription` 承载完整背景和要求。否则用户会在“节点可读”和“提示完整”之间被迫二选一。

## 第三阶段：为什么从插件转向 Tauri

随着地图、编辑器、安装与故障恢复成为核心体验，主要开发轨道转向 Tauri 2 桌面应用。React 负责界面，Rust 负责文件、网络、凭据和并发边界：

```text
React 19 + TypeScript + Zustand + Cytoscape.js
                    │
                    │ Tauri invoke / event
                    ▼
          Tauri 2 + Rust commands
                    │
        ┌───────────┼────────────────┐
        ▼           ▼                ▼
  Markdown Vault  DeepSeek API   操作系统凭据库
```

React 层保存会话、节点与选择状态，通过服务层调用 Tauri Command；响应先经过 Zod 校验，避免前端凭感觉解释后端结构。Rust 层处理 Markdown/YAML 编解码、DeepSeek 请求、文件监听、锁、冲突检测、总结、Canvas 和旧数据导入。

这不是为了“用 Rust 显得更重”，而是把最危险的能力放在更窄的边界里：路径是否合法、文件有没有被外部修改、Key 是否会泄露、两个请求能不能同时写同一场会话，都不应由任意 UI 组件各自实现。

## 最关键的实现：AI 回答先不进 Vault

很多 AI 笔记产品在模型返回后立即保存答案。LearnBranch 刻意多了一层 Answer Draft：

```text
提交问题
   ↓
节点先落盘（generating）
   ↓
DeepSeek 返回答案
   ↓
草稿写入应用数据目录，节点变为 ready
   ↓
用户编辑 / 预览 / 确认
   ↓
回答写入节点 Markdown，草稿删除
```

草稿位置在 Tauri 应用数据目录的 `answer-drafts/`，而不是用户的 Obsidian Vault。详情页会明确标记“AI 草稿待审核”，只有保存后才显示“已同步 Obsidian”。

这一层解决的不是技术问题，而是知识所有权问题：模型完成生成，只能说明一次请求成功，不能说明用户认可内容。把两个事件拆开后，系统状态也更诚实。

## Markdown 如何成为真正的事实来源

当前 Tauri Vault 使用平铺格式：

```text
<tauri-vault>/
├─ session-<sessionId>.md
├─ node-<nodeId>.md
├─ <可选的可读文件名>.md
├─ outputs/
│  ├─ summary-<sessionId>-<timestamp>.md
│  ├─ branches/<整支笔记>.md
│  └─ canvas/learning-map-<timestamp>.canvas
├─ .learnbranch-imports/
├─ .learnbranch-import-backups/
└─ .learnbranch-trash/
```

Session 和 Node 的结构字段放在 YAML frontmatter，确认后的回答放在 Markdown 正文。用户可以在 Obsidian 或普通编辑器中阅读；应用再次保存前会比较 `updatedAt`、问题、回答和文件版本，发现外部编辑就停止覆盖。

“Markdown 是事实来源”也意味着 Canvas 不能反过来控制数据。导出时，Rust 重新读取并校验会话树，用稳定的 preorder 和 depth 计算坐标，生成标准 JSON Canvas 1.0；每次输出版本化保存。Canvas 可以删掉重建，节点源文件不受影响。

## 并发与失败：真正花时间的地方

理想流程很短，可靠流程要回答更多问题：

- 用户连续点了两次重试，迟到的第一次响应能不能覆盖第二次？
- Obsidian 在 AI 请求期间改了同一节点，返回后写哪一版？
- 应用在草稿已生成、尚未确认时被强制结束，会不会丢内容？
- 删除十个后代时移动到一半失败，前五个怎么办？

当前实现用几层保护叠在一起：

1. 同一 Session 的生成与整理操作串行化。
2. 每次生成带 `requestId`，最终写入前确认磁盘中的请求仍匹配。
3. 文件锁与版本号阻止静默覆盖外部修改。
4. 失败节点保留在原位置，记录错误和尝试次数，重试复用原节点。
5. 删除先计算整棵子树，再移动到 `.learnbranch-trash`；部分失败尝试回滚。
6. 单会话限制 50 个节点，把性能与交互复杂度控制在已测试范围内。

真实验收还找出了两个只看单元测试很难意识到的问题：中文整理在 UTF-8 字节边界截断时可能 panic；重试如果复用旧逻辑，新的 `requestId` 会和自身冲突。这两处都说明，AI 产品的可靠性并不只在模型调用，更多时候藏在字符串、状态和磁盘边界。

## 从旧插件迁移：不要假装格式天然兼容

旧插件按会话建目录，Tauri 则在选定 Vault 中平铺 Session 和 Node。虽然两边都是 Markdown，也有相似字段，但“看起来可读”不等于“可以把目录直接交给另一套程序”。

最后采用的是显式单向导入：

1. 只读扫描旧目录并生成预览。
2. 检查 Schema、ID、树结构、节点数、目标冲突和源指纹。
3. 用户确认后，写入前先逐文件备份并校验 SHA-256。
4. 批量导入失败时删除本批次新目标，保留备份与源目录。
5. 写入 import marker，重复扫描保持幂等。

这条流程比“自动检测并升级”笨，但把不可逆的猜测换成了可检查的步骤。两套应用继续使用隔离目录，导入也不会被宣传成双向同步。

## 三次原生验收

自动测试证明代码满足契约，原生验收证明真实操作链没有在系统边界断掉。

### M1：真实 API 闭环

在 Windows Tauri 窗口中完成根问题、一级和二级分支，并走完“AI 草稿—人工修改—确认入库”。同时验证外部编辑冲突、失败重试、迟到响应保护、分支删除与恢复，以及整理结果的来源节点都真实存在。

### M2：数据与 Obsidian 交付

连续导出 Canvas 必须生成独立快照，不能覆盖前一版；旧插件 fixture 经预览、备份、导入后，节点、用户补充和旧总结仍可加载。最终 `.canvas` 在隔离的 Obsidian 1.9.10 中显示为真实 Markdown file node 和有向边。

### M3：Windows 分发技术链

从 NSIS 产物验证当前用户安装、冷启动、静默卸载、0.1.0 到 0.1.1 升级、降级阻断、重装，以及强制结束进程后的文件指纹。签名流程用的是临时自签名 QA 证书，只能证明技术链，不等于 Windows 信任的生产签名。

## 测试门禁不是一条命令，而是两条产品轨道

仓库根目录仍保留旧插件代码，因为已有数据可能需要严重缺陷和安全修复；`learn-branch/` 才是新功能主线。因此验证被拆成：

```powershell
# Tauri 主线
npm run check:desktop

# 旧版 Obsidian 插件
npm run check

# 整个仓库
npm run check:all
```

截至 2026 年 8 月 18 日保存的基线是：旧插件 154 项 Vitest、Tauri 前端 53 项 Vitest、Tauri Rust 120 项测试通过；桌面门禁还包括 ESLint、Prettier、TypeScript、rustfmt、Clippy 和无安装包原生构建。数字只是时间点快照，真正的意义是每条轨道有明确责任，不能把旧插件的验收拿来证明 Tauri 已经可发布。

## 做完这些之后，产品仍未“完成”

当前还缺 Windows 受信任生产签名与时间戳、自动更新与失败回滚、macOS/Linux 分发验收，以及最重要的 5～8 人两周内部 Alpha。

回头看，构建过程中最有价值的不是选了 Tauri、React 还是 Cytoscape，而是逐步收紧了几个边界：

- 图负责导航，阅读区负责工作。
- AI 生成与用户确认是两个事件。
- Markdown 是源，Canvas 是输出。
- 本地优先必须包含冲突、删除和恢复语义。
- 历史实现可以维护，但不能和当前主线混算进度。
